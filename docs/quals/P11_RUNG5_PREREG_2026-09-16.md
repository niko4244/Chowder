## 3. Weight projection (frozen)

The dense parent (`Qwen3.8-9B-abliterated-25-bf16`) is converted to the
reduced MoE via these steps:

### Step 1: Embedding projection
- Source: `model.embed_tokens.weight` [248320, 4096]
- Target: `model.embed_tokens.weight` [248320, 3072]
- Method: **Truncation** — keep first 3072 columns
- Rationale: PCA requires a calibration corpus; truncation is simpler and
  sufficient for a first-pass shape check. If rung 5 qualifies, a follow-up
  can test PCA projection.

### Step 2: Attention projection
- All Q/K/V/O projections: truncate first 3072 rows/columns as needed
- `q_proj`: [4096, num_heads×head_dim] → [3072, 16×192] = [3072, 3072]
- `k_proj`: [4096, num_kv_heads×head_dim] → [3072, 4×192] = [3072, 768]
- `v_proj`: same as k_proj
- `o_proj`: [num_heads×head_dim, 4096] → [3072, 3072]

### Step 3: Linear attention projection
- Same truncation pattern as Step 2, applied to the 24 linear_attention layers

### Step 4: MoE FFN creation
- The dense parent's FFN (`mlp.up_proj` [4096, 12288], `mlp.down_proj` [12288, 4096])
  is NOT directly used. Instead:
  - 16 routed experts: random init with `initializer_range=0.02`
  - 1 shared expert: random init with `initializer_range=0.02`
  - Router gate: random init
- Rationale: The dense FFN has intermediate_size=12288, but each MoE expert
  has moe_intermediate_size=632. Direct splitting would create correlated
  experts. Random init is honest about what we're testing: can the router
  learn to route effectively in the reduced-dimension space?

### Step 5: Norms and biases
- Copy directly from dense parent (no dimension change)

### Conversion script
`src/chowder/reduced_moe_convert.py` — to be committed on the same PR.

## 6. Thresholds (fixed before the run)

### T1 — validate before train
`chowder project-validate` passes; `chowder train` invoked only after.

### T2 — policy contract
Every worker result carries `load_policy_report.policy = "bf16-offload-transient"`,
`dtype = torch.bfloat16`, `placement_census` with all expert params on CPU,
gates on `cuda:0`, `verified: true`.

### T3 — measured preflight
Memory, step-cost, and model-load projections measured before step 1.
Refusal if: load + steps + evaluation projection exceeds 0.051 ceiling,
2.5 s/step, or 12.0 GB.

### T4 — trainability
Finite non-zero gate gradients on the exact gate path, real update,
32 router gates in scope; frozen-tensor digests report zero changed.

### T4a — routing-collapse threshold

| Metric | Threshold |
|---|---|
| `dead_experts_after` | **< 428** (same as rung-4; this is a new architecture, so rung-3c baseline does not apply directly) |
| `layers_with_grad_zero` | **≤ 2 of 32** |
| Any layer with `grad_zero_steps == 48` | Must be named with topology-vs-optimizer evidence |
| Missing per-layer records | **UNKNOWN** — refuses to certify |

**Note**: Since this is a new architecture with random FFN init, the initial
dead-expert count may differ from rung-4. The threshold is absolute (428),
not relative to a prior measurement on this architecture.

### T5 — horizon
48/48 steps, `stop_reason = max_steps`.

### T6 — paired gate contract
Exactly one evaluation worker for the candidate; `arm = "paired"`; base
measured **before** any payload read; single measured `model_load`; both
generations measured; baseline row completed from paired evidence.

### T7 — accounting
Total attributable device GPU-hours ≤ **0.051**, with loads explicitly budgeted.
Wall charges within the 0.179 envelope or exceedance honestly recorded.

### T8 — identity chain
Full-mode base content identity matches pinned manifest hash; payload bound
to re-derived base content; corpora hash to their pins; spec digest and
worker source identity verified.

### T9 — independent holdout quality

**Baseline re-measurement**: the frozen baseline (no candidate applied) must
be scored on the independent holdout corpus before the candidate training
run. This establishes the baseline holdout loss independently of the training
protocol.

**Threshold**: `candidate_holdout_loss < baseline_holdout_loss`

**Note**: The baseline here is the dense parent (not the HotCore artifact),
since we're converting from dense. The baseline holdout loss will differ
from rung-4's baseline.

### T10 — generation sanity probe

After the normal holdout evaluation, run a small generation sanity check
on both base and candidate using the same prompts and settings.

**Required metrics** (all measured, not derived from loss):

1. **Termination rate**: fraction of prompts that terminate with `eos` within
   the max-token limit (target: ≥ 0.90)
2. **Max-token-cap hit rate**: fraction of prompts hitting the generation limit
   without terminating (target: < 0.10)
3. **Distinct-trigram ratio**: unique trigrams / total trigrams across all
   completions (target: > 0.70 — indicates no severe repetition)
4. **Compression ratio**: output length / input length (reported, not gated —
   diagnostic only)
5. **Obvious looping**: any prompt producing 3+ consecutive identical trigrams
   = FAIL on that prompt (target: 0 looping prompts)
6. **Task score** (where applicable): any prompt with a verifiable answer
   scored correct/incorrect (reported, not gated — diagnostic only)

**Threshold**: `generation_sanity_pass = true` — all of (1), (2), (3), (5) must
meet their targets. (4) and (6) are reported for evidence but do not gate.

### T11 — architecture fidelity (NEW)

Verify the converted artifact matches the spec:
- `config.json` hidden_size == 3072
- `config.json` head_dim == 192
- `config.json` num_experts == 16
- `config.json` num_experts_per_tok == 2
- Weight shape audit: every tensor matches the expected shape
- No NaN/Inf in any weight tensor
