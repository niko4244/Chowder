`niko4244/Chowder` and pushed **before** the probe starts, so the commit order

## What this rung is (and is not)

Rung 3 asks one question: **can the real 9B-derived MoE artifact be trained as
a router pilot on the single RTX 5060 Ti (17.1 GB) at all?** It is answered by
a *measured* preflight of the artifact's real load/forward/backward memory and
step cost — not by parameter arithmetic, not by config claims. This rung does
**not** change `QUALIFIED_DEVICES` (cuda is already qualified by rung 2), does
not qualify model quality, and does not itself run the pilot.

## Load strategies (fixed order, all measured, none skipped silently)

The current worker hardcodes `dtype=torch.float32`. The preflight is a
standalone probe (not the worker); if and only if a strategy qualifies, the
worker load policy becomes a separate failing-test-first code slice before any
pilot. Strategy A is measured even though arithmetic predicts refusal —
measured numbers, not predictions, are the record.

- **A. fp32 full-resident** (current worker policy): expected ~37.6 GB. Measure
  actual peak and the failure mode.
- **B. bf16 full-resident**: expected ~18.8 GB resident.
- **C. bf16 + expert-tensor offload to CPU**: experts (≈7.95 GB) pinned on
  host, everything else on device (~10.9 GB). Host holds the offload in RAM
  (27.8 GB free measured). Router gates stay on device.

## Thresholds (fixed before the run)

1. **T1 identity**: manifest hash matches; all weight-file hashes re-verified.
2. **T2 headroom** (per strategy): peak CUDA allocator after
   load+forward+backward ≤ 14.0 GB on this card, leaving ≥0.6 GB over the
   measured context overhead. A strategy above this is *refused*, with its
   measured peak recorded.
3. **T3 real compute** (strategy C only): first forward+backward+update
   completes, loss finite, gate gradients observed on the intended gate path —
   the same standard the CPU worker applies, measured here on device.
4. **T4 step cost**: 3 warm steps timed; mean ≤ **3.0 s/step** (batch 2,
   seq 64 — the values the pilot will use). Above that, a bounded 12-step
   pilot would still fit the wall budget, but the number is recorded and the
   pilot's budget is derived from it, never from hope.
5. **T5 offload verified**: device census after load shows ≥ 32 expert tensors
   on CPU and all 32 gate tensors on GPU — counted from named parameters, not
   from code path.
6. **T6 accounting**: the probe records per-strategy peak allocated+reserved
   VRAM, load wall time, step times, and its own SHA-256; the report embeds
   them verbatim.

## Verdict logic (fixed before the run)

- Strategy C meeting T1, T2, T3, T5 → **rung 3 QUALIFIED** at the measured
  numbers; next slice: worker load policy (bf16 + offload) behind failing
  tests, then the bounded 12-step router pilot (rung 3b) with a fresh
  preregistration whose wall/memory budgets are the measured values ×1.5.
- Strategy C refused or crashing → **rung 3 REFUSED**: the 9B pilot does not
  fit this hardware today; the report records the measured reason and the
  candidate fallbacks (CPU bf16 pilot with reduced scope; hardware change) as
  options, not plans. No code path is loosened to make it fit.
- A and B outcomes are recorded as evidence regardless.
